# Delivery action plan

**Proposed plan, not a delivery promise.** The target and feature boundary are in the [product definition](../PRODUCT_PLAN.md). Feature IDs F refer to the [catalog](FEATURES.md), S to the [Simulink-style plan](SIMULINK_FEATURES.md), D to [discovery](DISCOVERY.md), A to [assurance](ASSURANCE.md), and R to the [audit baseline](AUDIT_BASELINE.md). Roles below are responsibilities to assign, not people already allocated. All acceptance criteria are proposed future gates.

**Milestones and completion gates.** Discovery can run alongside M0. UI prototypes and data acquisition can proceed while contracts mature, but production integration must wait for the relevant decisions. Do not promote a release because its UI looks finished while its evidence or support remains incomplete.

Current authorized platform order is **macOS first, Linux next**. The bounded
continuous-model feasibility work and remaining M1 gates are recorded in
[M1 implementation](M1_IMPLEMENTATION.md) and [M1 contracts](M1_CONTRACTS.md).
Windows is no longer a supported platform: its engine CI leg, presets and
release packaging were withdrawn after an installed-package consumer failure
that was never root-caused. Engine and product now target the same two
platforms.
The [M2 preview increment](M2_IMPLEMENTATION.md) adds project revisions, a shared
CLI worker, typed linear-system/LQR graph import, explicit retained-revision
restoration and native block/sample tables in the macOS feasibility surface.
Synthetic and local linear aircraft/controller workflows cover a bounded
part of M2; toolkit selection, hosted verification, complete accessibility/recovery and
clean-machine installation acceptance remain open. The
[project-file contract](../PROJECT_FILES.md) records the implemented boundary.

A stage's computational completion is separate from numerical reliability, model validity and engineering acceptance; a diagnostic exploration may finish computing while its requirement outcome remains unresolved or failed.

**First ten working days: planning and executable evidence, not a v1 deadline.** This kickoff sequence assumes parallel ownership; with a solo developer, execute the same packages sequentially and obtain independent review externally. Dependencies govern the order even if the window expands.

| Window | Engineering work | Product/evidence work | Reviewable output |
|---|---|---|---|
| Days 1–2 | W01 reproductions; inspect release provenance for W06; capture controlled baseline | W07 acceptance task, intended reliance, platforms and data contacts; assign owners/reviewers | Ranked defect board, baseline evidence and explicit assumptions register |
| Days 3–5 | W02–W05 focused patches and independent regression expectations; W06 gate design | W13 data route; initial W08 artifact examples and W09 event/loop fixtures | Small reviewable fixes; draft acceptance/semantics contracts and unresolved questions |
| Days 6–8 | Integrate reviewed fixes; exercise complete relevant gates; headless compiler feasibility spike | W11 desktop comparison on the same task; numerical/model benchmark protocols and licensing review | M0 closure candidate, measured architectural alternatives and data/benchmark risks |
| Days 9–10 | Review M0 evidence; demonstrate smallest graph-runtime prototype if semantics permit | Review M1 scope, role capacity, external data/verification cost and milestone estimate | Go/narrow/stop decisions; funded milestone backlog with named owners and dates |

Do not manufacture estimates from feature counts. At the day-10 review, split Large packages until their behavior and evidence are independently reviewable, estimate them with their owners, and include integration, reference-data acquisition, independent review, installer/security work and support cost. A missed data or assurance prerequisite changes the supported product scope or schedule openly.

**Staffing and parallel work.** A practical planning model has product/domain ownership, control/numerical engineering, simulation/model-data engineering, desktop/platform engineering, and independent verification/assurance coverage, with release/security/UX expertise available. One person may hold several roles, but a developer's self-review does not establish verification independence when it is required. Do not assume all listed roles are full-time. For a small team, prioritize one platform, one aircraft family/configuration profile and a compact supported block set; verify cross-platform support before advertising it. A larger team can run audit/benchmarks, model evidence, runtime semantics and desktop work in parallel after contracts stabilize. The rate of acquiring trustworthy aircraft evidence may remain the critical path regardless of developer count.

**Critical dependencies and architectural decisions.** Reliable result semantics and independent oracles precede broad synthesis claims. Units/frame/model identity precedes reusable connections and import. Block state/direct-feedthrough/clock semantics precedes hybrid controllers and code generation. Representative data and performance workloads precede desktop/storage choices. Campaign determinism must be specified before parallelism/caching; stable ordering, seeds, reduction policy and resume behavior are part of the contract. Compatibility policy precedes persistent public schemas. Native plugin execution, state machines and generated code each require a separate trust/semantics review rather than inheriting assurance from the study registry.

Use the [existing ADR process](../adr/README.md) to record the result artifact/identity design, model IR and clock rules, desktop/worker boundary, project storage/migrations, model-table interpolation/extrapolation, controller scheduling, distributed/parallel determinism, extension ABI and import/code-generation profiles. Existing ADRs remain authoritative until a reviewed decision supersedes them. Framework selection is intentionally deferred to the evidence from W11.

**Definition of done for each numerical feature.** Its requirement and supported domain are written; accepted reference data and independent comparison are identified; error budgets are justified before measuring results; boundary/negative/conditioning cases are exercised; units/frames/sample semantics are explicit; diagnostics and provenance survive all interfaces; documentation and generated evidence reflect actual behavior; existing regressions remain intact. An unresolved mathematical/model result is retained and displayed as such, never converted into an engineering pass. For UI/platform features, use task-based usability, accessibility, recovery, compatibility and security checks appropriate to the change rather than duplicating numerical tests in the UI.

**Release acceptance and change control.** At M5 verify new install, prior-version upgrade, project migration, offline run, replay, export/import, cancellation/crash recovery, disk/resource failures, denied writes, invalid data, unsupported models, signed artifact verification and rollback on each advertised platform. Publish a compatibility/support policy and known limitations with the exact accepted runtime/data profiles. Any waiver has an owner, affected requirement/use case, rationale and compensating evidence; it cannot silently turn unknown validity into a successful result. Product acceptance, customer aircraft-model acceptance and any tool qualification are separately recorded decisions.

**Issue and progress format.** Every issue should identify the W/F/S requirement, R/A risk if relevant, user-visible behavior, supported/unsupported cases, source surface, dependencies, owner/reviewer, independent reference and budget, acceptance evidence, migration/report implications and milestone. Track defects closed with independent evidence, workflow acceptance, benchmark/domain coverage, unresolved-case handling, reproducibility, user-task outcomes and release readiness. Raw test counts and UI screenshots alone are insufficient completion metrics.
