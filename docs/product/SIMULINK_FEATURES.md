# Simulink-style modeling and simulation plan

**Proposed product features, not current capabilities.** The request to add Simulink features is interpreted as a usable graphical model-based engineering environment, including execution and verification semantics. The core visual modeling workflow is part of the proposed v1, not an optional diagram viewer. The [feature catalog](FEATURES.md) sets overall priorities; this document specifies the model-runtime work in more detail.

Simulink provides a block-diagram modeling/simulation environment. Test harnesses and code generation also belong to separately documented MathWorks products, so the requested product direction spans more than a canvas. The Galata proposals below are an independently designed scope, not a claim of file, block, solver or numerical equivalence with the entire MathWorks ecosystem. [Simulink](https://www.mathworks.com/products/simulink.html), [Simulink Test](https://www.mathworks.com/products/simulink-test.html), [Simulink Coder](https://www.mathworks.com/products/simulink-coder.html).

**The model compiler is a first-class subsystem.** The present [pipeline](../../include/galata/pipeline/pipeline.hpp) is a DAG of engineering operations. A signal-flow graph can contain feedback and dynamical state; it needs a different representation and compilation stage. Preserve that distinction:

1. Parse the versioned model, parameters, library references and declared configurations.
2. Resolve stable block/port IDs and model instances; preserve source hierarchy for traceability.
3. Propagate/check types, dimensions, units, coordinate frames, sample times and initialization rules.
4. Identify continuous states, discrete states, direct-feedthrough dependencies and strongly connected algebraic components.
5. Reject unsupported equations/rates/blocks with specific diagnostics; build an explicit execution schedule for accepted models.
6. Lower accepted blocks into an IR that calls the numerical kernels; record compiler/runtime/IR version and all solver settings.
7. Execute the same compiled model from the desktop, CLI, harness runner and campaign worker; publish typed artifacts with the same evidence contract.

The block model format is canonical and diffable; canvas coordinates and presentation settings are stored separately from numerical identity. The architecture decision must specify how library updates, schema migrations, cached IR, parameter overrides and imported blocks affect identity. Generated IR is a rebuildable artifact, not the only copy of an engineer's model.

**Timing semantics must be written before blocks are multiplied.** The first supported hybrid profile uses an explicit base tick and validated commensurate discrete periods/offsets, with continuous substeps aligned to sample/event boundaries. Evaluate combinational outputs from a documented snapshot, then commit discrete state updates in a deterministic phase; define output/update ordering explicitly for every supported block. A discrete controller must not update at each RK substage. Noise generators draw on their declared clocks with independent recorded seeds, not according to incidental evaluator call count. Rate-transition blocks declare hold/interpolation and initial values. Unsupported clocks are rejected, not silently rounded. The discovery spike must compare multirate, zero-order-hold and simultaneous-event fixtures against an independent implementation. [Sample-time concepts](https://www.mathworks.com/help/simulink/ug/how-to-specify-the-sample-time.html).

Every block declares whether outputs depend on current inputs and how state is initialized/reset. Pure direct-feedthrough cycles require an algebraic solution; graphical feedback through an integrator or unit delay has different semantics. V1 detects unsupported algebraic loops and explains them. A later solver may accept a declared equation class only with residual, convergence and failure checks. Adding a hidden delay to make a loop executable would change the engineering model and is forbidden. Simulink's own documented algebraic-loop handling involves numerical solution, underscoring why this is runtime work rather than drawing functionality. [Algebraic-loop concepts](https://www.mathworks.com/help/simulink/ug/algebraic-loops.html).

**The initial library has an explicit supported profile.** Start with floating-point real signals, Boolean logic, named vector/bus interfaces, continuous linear/aircraft state and discrete controller state. Integer conversion and arithmetic require an overflow policy. Complex signals, variable-size arrays, arbitrary user scripting, recursive models, implicit physical networks and unrestricted native extensions need separate contracts. Each library entry exposes ports, parameter units/ranges, direct feedthrough, state, sample behavior, validity, provenance and independent verification evidence. A model that uses one unsupported block is rejected as a whole until the user makes a reviewed substitution.

**Interactive tuning must remain replayable.** Ordinary editing creates a new configuration for the next run. Live tuning is enabled only for parameters whose runtime semantics are declared, applied at a defined tick, and recorded as events. Structural edits require recompilation. Pausing is a presentation/control action; it must not change simulation time or numerical results. Checkpoints contain all state and runtime identity and are incompatible across unapproved model/runtime changes. Stopped, cancelled, crashed and complete runs remain distinguishable. A test harness should reproduce the same event history without UI interaction.

**Interoperability has three different meanings.** Data exchange exports/imports matrices, trajectories, parameters and operating points with explicit units and rates. Behavioral co-simulation exchanges signals with another simulator under a declared master clock and coupling scheme. Native model translation maps supported block semantics and must inventory losses. FMI defines Model Exchange, Co-Simulation and Scheduled Execution interfaces; choosing one does not establish numerical equivalence or solve the master algorithm. [FMI specification](https://fmi-standard.org/docs/3.0.2/).

Use documented APIs on an appropriately licensed MATLAB/Simulink installation to explore extracting a supported model subset; test selected versions and report unhandled scripts, callbacks, custom blocks, library links, data dictionaries, variants and state-machine constructs. The standalone Galata application should not require MATLAB for its native workflow. A translated diagram is accepted only after structural and behavioral comparison; visual similarity is insufficient. Avoid promising universal SLX compatibility or silently dropping unsupported constructs.

**Code generation is a later, bounded compiler product.** First target an explicitly supported sampled-controller subset, with defined numeric types, static state layout, initialization/reset and one-step semantics. Plant simulation and arbitrary third-party blocks are not implicitly eligible. Retain block-to-IR-to-code mapping, compiler flags, generated-source hashes and test results. Validate host software-in-the-loop equivalence first, then processor-specific behavior, timing/resource budgets and hardware interfaces under a named target contract. Code generation support does not establish flight-code approval. MathWorks documents C/C++ generation and test workflows separately, which is a useful reference for the separation of responsibilities. [Coder documentation](https://www.mathworks.com/products/simulink-coder.html).

**Implementation sequence.** Establish S02/S06 semantics and independent fixtures during M1. Deliver S01/S03/S07/S08 with one continuous closed-loop model at M2. Add S04/S05/S06/S11/S12 with sampled aircraft-control studies at M3. Complete S09/S10/S13/S14/S15 and campaign integration at M4. M5 accepts the installed workflow and evidence. S16–S20 have their own discovery decisions, estimates and acceptance gates; they do not delay defining a complete, bounded first product.

The [proposed executable-model architecture](../architecture/EXECUTABLE_MODEL.md)
turns this capability plan into dependency boundaries, typed IR, solver and
clock phases, artifact identity, replay contracts and a migration sequence.
It is a design for review, not a claim that the graph runtime exists.
